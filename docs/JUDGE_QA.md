# 评委问答

## 为什么必须是多 Agent？

地图事实、冲突风险、负重约束和干员技能属于不同能力域。单 Agent 可以生成
一段文字，但难以把事实来源、相互冲突和仲裁依据拆分出来。这里三个中间 Agent
并行产生草稿，交换结果后修正，校验 Agent 再独立仲裁。

## 这是不是写死的流程？

执行阶段、最大轮次、Agent 版本、能力与工具权限都来自注册表。当前比赛版本
提供一条经过验证的撤离领域工作流模板，调度器会在可用版本间按能力和优先级
选择。工作流通过版本接口注册，历史运行会记录具体版本。

## 智能体现在哪里？

1. 根据任务打法调整风险审查权重。
2. 根据能力标签选择 Agent 版本。
3. 三个 Agent 根据彼此草稿修正结论。
4. 失败类型触发重试、换路、补物资或人工规则。
5. 调度和仲裁依据进入事件日志，而不是黑盒输出。

## 如何确保结果可信？

客观约束优先使用确定性工具，例如负重计算、撤离条件和地图查询。LLM 不能
直接覆盖这些验证结果。校验 Agent 还必须逐项给出通过或拦截证据。

## 如何复现？

每次运行保存输入、Agent 版本、工作流版本、完整事件、轮次状态与工具调用。
前端可以按事件逐条回放。失败快照可以创建新的恢复分支，原运行不会被覆盖。

## 为什么先做本地规则再调用模型？

比赛现场需要稳定。本地规则保证网络或模型异常时仍能完整运行，同时为 LLM
提供可信事实骨架，降低地图点、消息编号和撤离条件被模型改写的风险。

## 是否真的使用了 MCP？

项目提供独立 `mcp_server.py`，通过 stdio JSON-RPC 提供工具列表和工具调用。
后端内部与 MCP Server 共用同一 Tool Registry，避免出现两套工具实现。

## 数据是不是真实游戏数据？

当前地图资源和撤离条件标记为竞赛演示配置。正式提交前必须按比赛使用的游戏
版本核对。系统把地图数据独立配置，后续修正不需要改 Agent 控制流程。

## 如何证明自我循环有效？

标准评测包含五张地图、超重、干员不足和高风险打法八类场景。报告输出预期结果、
实际结果、轮次、快照数和耗时。首轮失败与最终收敛都保存为可回放事件。

## 后续怎样扩展到其他行业？

替换工作流阶段、Agent 定义和 Tool Registry 即可复用运行、调度、验证、
事件持久化、回放和评测基础设施。行业知识通过地图/文档配置与工具接入。
